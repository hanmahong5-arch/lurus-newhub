> 工程师版（带 curl 的逐条验收）见 `business-acceptance-tests.md`；本文是点击式的上手指引。
> 本文里的"预期数字"全部来自种子脚本 `scripts/uat/seed.ts` 写入的已知值（脚本说明见 `scripts/uat/README.md`）。**测试开始前，工程师必须先跑过种子脚本并把 `accounts.md` 发给你**——没有它，下面的账号和数字都对不上。

## 2. 怎么登录

UAT 没有开单点登录（SSO），也没有账号密码，**只能用"桥接登录"**：

1. 打开 `https://test-newhub.lurus.cn/bridge-login`。
2. 页面里粘贴工程师发给你的**测试令牌**，并填入你自己的 `user_id`（见 `accounts.md`）。
3. 点击登录，进入控制台。

工程师也可能给你一条一键链接，形如 `https://test-newhub.lurus.cn/bridge-login#t=<令牌>&u=<你的user_id>`：直接打开即登录。这条链接里含令牌，等同密码，**只发给本人**。

每个角色用哪个账号：

| 角色 | 账号（`accounts.md` 里的姓名） | 用来测什么 |
|---|---|---|
| 平台运营 | 平台运营 | 渠道与账号池、平台规则、跨租户查看 |
| 只读观察员 | 只读观察员 | 看审计，验证"只看不改"（近似，见 3.3） |
| 企业管理员（付款人）× 2 | 李明（演示科技）、赵强（传统制造） | 建部门、批量发 key、账单、数据与安全 |
| 部门负责人 × 2 | 王磊（演示科技 研发部）、孙伟（传统制造 生产部） | 只看本部门 |
| 员工 key × 6 | 张三、李四、王五、钱一、周二、吴三 | 用 key 调用模型。**员工没有登录账号，只有 key** |
| 网关 key / 普通 key | 演示科技 网关、演示科技 普通 key（传统制造同理） | 身份头归属对照 |
| 测试员 × 6 | 测试员A～F | 普通用户：仪表盘、模型广场、兑换码；**测试员F 的 key 只有 1 单位额度，专门演示 402** |

> 注意：同一台电脑/同一出口 IP，每分钟最多登录 5 次。来回切换账号不要太快；换账号请先退出，或用浏览器的"无痕窗口/不同浏览器配置"同时开多个角色。

## 3. 能测与不能测

### 3.1 UAT 能测

- 登录（桥接）、仪表盘、模型广场、API 密钥、使用日志。
- 企业管理：部门、批量发 key、月账单与 CSV、数据与安全（留存、内容规则）。
- 兑换码、额度不足（402）、防重放。
- 可信网关身份头归属、部门负责人范围、越权 404、跨租户隔离。
- 渠道与账号池（运营人员）：批量导入（先试运行）、健康原因、恢复。
- 渠道冷却与切换（需要工程师在场，见场景 11）。

### 3.2 UAT 不能测（以及去哪测）

UAT 是隔离实例，**刻意**关掉了会碰真实资金或真实外部系统的部分：

| UAT 关了 | 后果 | 去哪测 |
|---|---|---|
| 统一计费（BILLING_UNIFIED） | **不会真的扣钱包**。余额只是本系统自己的额度账本，"钱包为准"（以平台钱包余额为准）的行为在这里不成立 | 本地验收栈（`scripts/acceptance-stack.sh`，带假钱包）+ 生产小额探针 |
| 单点登录（OIDC/SSO） | 不能测 SSO 登录、登出、会话跨站 | 生产（hub.lurus.cn）小额探针 |
| NATS 事件 | 额度变更事件不会外发，下游订阅方看不到 | 本地验收栈、生产 |
| 注册 | 已关闭，不能自助注册新用户 | 工程师用种子脚本建号 |

> 所以：**本文所有金额都是"本系统额度账本"的变化，不代表真实扣款。**

### 3.3 已知近似与限制

- **"只读观察员"是近似**：产品里没有真正的只读角色。观察员是"管理员级账号 + 审计只读授权"，可以看审计，但不能管理租户和渠道；它不是严格只读，不要拿它做"只读合规"结论。
- **模型要能回答 200 才能测计费类场景**：故障模拟器带有"成功模式"（模型名以 `ok` 或 `ok-` 开头），种子脚本会把 `uat-demo-chat` 映射到它的 `ok-chat`，无需真实上游即可返回 200，用量固定为输入 1000、输出 500 token（可预测金额）。前提是 UAT 部署已设置 `FAULTSIM_TOKEN`（运维步骤，见 `deploy/k8s/r6-uat/README.md`），并在导出该变量后运行过种子脚本；也可改用 `--upstream-base-url` 接真实或假上游。**开测前先确认**：用任一测试员的 key 调一次 `uat-demo-chat`，应该返回 200。若不是，场景 4～8、10、12、13 暂停，先找工程师。
- **同一出口 IP 的登录限流**：每分钟 5 次（见第 2 节）。
- **Secure cookie**：登录 cookie 只在 https 下有效，必须用域名访问；用 `http://localhost` 隧道的浏览器会"登录了又掉线"。
- **部署期间会断一次**：UAT 只有 1 个副本，每次部署（合并到主线后自动发生）会有几十秒不可用，请求报 502/503 属于正常，等一分钟重试，不要提缺陷。
- **夜间自动化测试会占用限流**：每天 03:00（北京时间，19:00 UTC）有一轮自动化端到端测试，会从同一出口大量请求并创建/删除数据。**这个时间段不要测试**，也不要把夜里"数据变了"当缺陷。
- 新渠道要等渠道缓存刷新（约 60 秒）才会被路由到。

## 4. 通用约定

- "**预期数字**"里的 `N 单位 ≈ M 美元`按 500 000 单位 = 1 美元换算。
- "**日志**"= 新控制台"使用日志"（`/next/usage-logs`），旧控制台 `/console/v2/log`。
- "**调用模型**"的写法（需要一台能上外网的电脑，用终端或工程师给的工具）：

```bash
BASE=https://test-newhub.lurus.cn
KEY=<key 的明文，由工程师分发>
curl -sS -i "$BASE/v1/chat/completions" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"model":"uat-demo-chat","messages":[{"role":"user","content":"你好"}]}'
```

  返回头里的 `X-Request-Id` 请一并记下，提缺陷时要用。新控制台的"API 密钥"页（`/next/keys`）里每把 key 的详情也有调用示例，可以直接复制。
- 每个场景末尾的"通过标准"全部满足才算通过；任何一条不满足就按第 7 节提报，不要自己改数据绕过去。

## 5. 场景

### 场景 1　登录与仪表盘

- **目的**：确认桥接登录可用，仪表盘能打开且数字与账号表一致。
- **前置账号**：测试员A。
- **步骤**：
  1. 按第 2 节登录测试员A。
  2. 进入"仪表盘"（`/next/dashboard`；旧控制台 `/console/v2/dashboard`）。
  3. 进入"API 密钥"（`/next/keys`），找到名为 `uat-key-t01` 的密钥。
- **预期画面**：登录后落在工作台；侧栏只有"工作台"分组（仪表盘、API 密钥、使用日志、模型），**没有**"企业管理"和"平台运营"。
- **预期数字**：`uat-key-t01` 的额度为 **5 000 000 单位 ≈ 10 美元**，已用 0；密钥只显示掩码（形如 `sk-xx****yyyy`），不显示明文。
- **通过标准**：以上都成立；退出后再用无令牌访问 `/next/dashboard` 会被带回登录。

### 场景 2　模型广场

- **目的**：确认用户能看到可用模型和价格。
- **前置账号**：测试员A。
- **步骤**：进入"模型"（`/next/models`；旧控制台公开页 `https://test-newhub.lurus.cn/pricing`）。
- **预期画面**：列表中有 `uat-demo-chat`，带价格；若工程师启用了故障模拟渠道，还会看到 `http_500`、`rate_limit_429`、`mid_stream_abort`、`slow_headers`（这是故障演示用的"假模型"，业务人员不要调用）。
- **预期数字**：`uat-demo-chat` 的价格倍率 **0.15**、输出倍率 **4**，即输入 **0.30 美元/百万 token**、输出 **1.20 美元/百万 token**（若工程师在种子时改了价格，以工程师的说明为准）。
- **通过标准**：模型和价格可见，且与账号表/工程师说明一致。

### 场景 3　企业管理员建部门与批量发 key（明文只显示一次）

- **目的**：企业管理员自助建部门、批量给员工发 key，明文 key 只出现一次。
- **前置账号**：李明（演示科技管理员）。
- **步骤**：
  1. 登录李明，侧栏出现"企业管理"：成员与邀请、部门、批量发 Key、账单与对账、数据与安全。
  2. 进入"部门"（`/next/org/departments`；旧控制台 `/console/v2/projects`），确认已有"研发部"（部门编码 `DT-RD`）和"市场部"（`DT-MK`）。再新建一个"测试部"，编码填 `DT-QA`。
  3. 进入"批量发 Key"（`/next/org/keys-batch`）。准备一份名单：`dt-e90, dt-e91`（员工标识），部门选"测试部"，额度 1 000 000，提交。
  4. **立即**把页面上出现的两把明文 key 复制保存。关闭对话框或刷新页面后再看。
  5. 再提交同一份名单一次。
- **预期画面**：第 3 步成功后显示两把明文 key；第 4 步刷新后密钥列表只剩掩码；第 5 步提示这两位员工已存在、**被跳过**，没有新 key。
- **预期数字**：新建 2 把 key，每把额度 **1 000 000 单位 ≈ 2 美元**；员工标识只允许字母、数字和 `. _ @ : -`，最长 64 位；一次最多 500 人，整批要么全成功要么全不成功。
- **通过标准**：明文只在创建时出现一次；重复提交不产生重复 key；key 归属付款人（密钥列表的所有者是李明）。
- **注意**：这一步会新增数据，做完在"部门/密钥"里留着即可，不要删原有的 `dt-e01～e03`。

### 场景 4　402 → 兑换码 → 重试 → 防重放

- **目的**：额度用完时提示明确；兑换码入账；同一兑换码不能再用。
- **前置账号**：测试员F（key `uat-key-t06`，额度 1 单位）、一个未使用的兑换码（`secrets.csv` 里 `uat-code-*`，每个 500 000 单位 ≈ 1 美元）。
- **步骤**：
  1. 用测试员F的 key 调一次 `uat-demo-chat`（第 4 节的 curl）。
  2. 登录测试员F，进入兑换入口（旧控制台"钱包/兑换"，路径 `/console/topup`；新控制台以工程师告知的入口为准），输入一个兑换码。
  3. **再调一次**同一把 key。
  4. 在"API 密钥"里把这把 key 的额度提高到 1 000 000，再调一次。
  5. 把**同一个**兑换码再兑换一次。
- **预期画面**：
  - 第 1 步：HTTP **402**，错误码 `token_quota_exhausted`，说明是"这把 key 自己的额度不足"。
  - 第 2 步：兑换成功，提示入账 **500 000 单位（1 美元）**。
  - 第 3 步：**仍然 402**——兑换码充的是账号钱包，不会自动给这把 key 加额度（这是预期行为，不是缺陷）。
  - 第 4 步：调用成功（200）。
  - 第 5 步：被拒绝（400），余额**不增加**。
- **预期数字**：兑换前后账号额度恰好相差 **500 000**；防重放后相差 **0**。
- **通过标准**：402 的错误信息可读；兑换入账金额精确；重放被拒且不入账。

### 场景 5　员工 key 调用后，日志按部门、按员工可见

- **目的**：企业管理员能按部门、按员工看到谁用了多少。
- **前置账号**：李明；员工 key `dt-e01`（张三，研发部）、`dt-e03`（王五，市场部）。
- **步骤**：
  1. 用 `dt-e01` 调 `uat-demo-chat` 3 次，用 `dt-e03` 调 2 次。
  2. 登录李明，进入"使用日志"（`/next/usage-logs`；旧控制台 `/console/v2/log`），按部门筛选"研发部"，再按员工筛选 `dt-e01`。
- **预期画面**：研发部下能看到 `dt-e01` 的记录，市场部下只有 `dt-e03` 的记录。
- **预期数字**：研发部 **3 次**、市场部 **2 次**；日志里每条的部门/员工与所用 key 一致（部门编码 `DT-RD`/`DT-MK`，员工标识 `dt-e01`/`dt-e03`）。
- **通过标准**：次数对得上；金额 = 用量 × 价格（以日志里的用量按场景 2 的价格自行核算）。

### 场景 6　可信网关身份头归属 与 普通 key 带头被忽略

- **目的**：企业网关 key 用请求头标明"是谁、哪个部门"，系统据此归属；普通 key 即使带了同样的头也**不能**冒名。
- **前置账号**：李明；`dt-gateway`（可信网关 key）与 `dt-plain`（普通 key）。
- **步骤**：
  1. 用 `dt-gateway` 调一次，附加头 `X-Lurus-Employee: dt-e02` 和 `X-Lurus-Dept: DT-RD`。
  2. 用 `dt-plain` 调一次，附加**同样**的两个头。
  3. 用 `dt-gateway` 再调一次，**不带**任何头。
  4. 登录李明看日志。
- **预期画面**：第 1 步的记录归到员工 `dt-e02`、研发部；第 2 步的记录**不**归到 `dt-e02` 或研发部（头被忽略，归属为该 key 自己的标识 `dt-plain-emp`、无部门）；第 3 步的记录在"未分配/无部门"。
- **预期数字**：三次调用各 1 条日志；按部门汇总时研发部 +1（只有第 1 步）。
- **通过标准**：只有可信网关 key 的身份头生效。普通 key 带头能改变归属 = 严重缺陷（越权冒名）。

### 场景 7　部门负责人只看本部门（越权 404）

- **目的**：部门负责人只能看自己部门；看别的部门拿到的结果与"不存在"无法区分。
- **前置账号**：王磊（演示科技，研发部负责人）。
- **步骤**：
  1. 登录王磊，侧栏有"部门"和"账单与对账"，**没有**"成员与邀请""批量发 Key""数据与安全"。
  2. 在"使用日志"里只看到研发部记录。
  3. 在账单里选"市场部"（或让工程师给你市场部的部门 id，在地址栏改成该 id）。
  4. 尝试导出"整个租户"的日志。
- **预期画面**：第 2 步只有研发部；第 3 步显示"未找到"（404），与输入一个根本不存在的部门 id 的表现**一模一样**；第 4 步被拒（403）。
- **预期数字**：王磊看到的研发部条数 = 场景 5 里研发部的条数（含全部成员，不只他自己）。
- **通过标准**：越权看别的部门是 404 而不是"无权限"（不泄露该部门存在）；租户级导出 403。

### 场景 8　月账单：分组与合计一致，可下载 CSV

- **目的**：账单按部门、员工、key 三种分组，合计彼此相等，CSV 与页面一致。
- **前置账号**：李明。
- **步骤**：
  1. 进入"账单与对账"（`/next/org/billing`；旧控制台 `/console/v2/billing`），选当月。
  2. 依次切换分组：按部门、按员工、按 key。
  3. 点"下载 CSV"，用 Excel 打开。
- **预期画面**：三种分组各有明细行，页脚有合计行。
- **预期数字**：三种分组的"请求数合计""额度合计""金额合计"**完全相同**；每种分组内，明细行相加 = 合计；CSV 最后一行合计 = 页面合计。场景 5、6 做过的调用都应包含在内（本月研发部至少 3+1 次）。
- **通过标准**：任意一处不等都是缺陷（记下分组方式和两个不等的数字）。
- **注意**：账单和导出有每 20 分钟的频率限制（UAT 放宽到 200 次），连续狂点导出才会触发。

### 场景 9　客户管理员进不了平台运营页

- **目的**：客户的管理员不是平台员工，进不了运营功能。
- **前置账号**：李明（客户管理员）；对照账号：平台运营。
- **步骤**：
  1. 登录李明，看侧栏：**没有**"平台运营"分组。
  2. 手工在地址栏输入 `https://test-newhub.lurus.cn/next/ops/channels`，回车。
  3. 旧控制台同理：输入 `https://test-newhub.lurus.cn/console/v2/channel`、`/console/v2/admin/users`。
  4. 换"平台运营"账号做同样的访问。
- **预期画面**：李明得到"无权限/403/回到工作台"，**不会**看到渠道列表，也不会看到一屏失败的请求；平台运营可以正常打开。
- **预期数字**：无。
- **通过标准**：客户管理员无法看到或操作任何渠道、全平台用户、其他租户数据。

### 场景 10　禁用/删除 key 后立即失败

- **目的**：撤销一把 key 后，下一次调用马上失败，不能"再用一会儿"。
- **前置账号**：李明；用场景 3 新建的 `dt-e90`。
- **步骤**：

  2. 李明在"API 密钥"里**禁用** `dt-e90`。立即再调一次。
  3. 重新启用，调一次（200）。
  4. **删除** `dt-e90`。立即再调一次。
- **预期画面**：第 2 步和第 4 步返回 **401**；上游没有被调用，日志里不新增扣费记录。
- **预期数字**：第 2、4 步额度不变（用量 0）。
- **通过标准**：禁用/删除后的**第一次**调用就失败（允许几秒内的缓存延迟不超过 5 秒；超过就提缺陷并附时间）。

### 场景 11　渠道冷却与切换（**由工程师现场演示**，业务人员观察）

- **前置**：种子脚本已建好 `uat-demo-upstream`（正常）、`uat-demo-faulty`（**默认禁用**，高优先级，会返回 500）；故障模拟需要服务端配置过 `FAULTSIM_TOKEN`，**没有配置时此场景无法演示，标"阻塞"**。

- **预期数字**：用户可见的失败次数应为 0；被冷却渠道的失败次数在冷却触发后不再增加。
- **通过标准**：用户无感；失败渠道被隔离而不是每次都先打它；演示结束后状态已还原。

### 场景 13　数据与安全：留存与内容规则（观察 → 强制）

- **目的**：企业管理员设置内容留存期限和内容规则；规则先"观察"（只记录不拦），确认无误后切到"强制"（拦截）。
- **前置账号**：李明。

  2. 查看/修改"内容留存"设置，保存。
  3. 新增一条内容规则：关键词/正则填 `UATBLOCK`，模式选**观察**，保存。
  4. 用 `dt-e01` 调一次，消息内容里带 `UATBLOCK`。

### 场景 14　渠道与账号池（**运营人员**）：批量导入（先试运行）、健康原因、恢复

- **目的**：运营人员批量导入渠道密钥时先"试运行"看结果，再正式导入；渠道/密钥不健康时能看到**原因**，修复后可恢复。
- **前置账号**：平台运营。
- **步骤**：
  1. 进入"渠道与账号池"（`/next/ops/channels`；旧控制台 `/console/v2/channel`）。
  2. 选一条渠道，打开"批量导入密钥"，粘贴 3 行假密钥（每行一个，随意字符串），**保持"试运行"开启**，提交。
  3. 查看试运行结果（逐行：将新增/重复/格式错误）。**确认密钥列表没有变化**。
  4. 关闭"试运行"，再提交一次。
  5. 查看渠道健康：对一把失效的假密钥点"测试"，在健康信息里查看**原因**（例如认证失败）。
  6. 对该密钥点"恢复"，再测试。
- **预期画面**：第 3 步只出现预览，不落库；第 4 步密钥数增加 3；第 5 步健康状态为异常且给出具体原因，不是笼统的"失败"；第 6 步恢复后状态回到"待检测/可用"，之后测试又会因假密钥失败并再次给出原因。
- **预期数字**：试运行密钥数不变（+0）；正式导入 +3。
- **通过标准**：试运行不改数据；健康原因可读；恢复可用。
- **测完**：把导入的 3 把假密钥删除。

## 7. 问题提报

每个问题请一次给全下面四样，缺一样我们没法定位：

1. **截图**：整页，能看到地址栏和你的账号。
2. **X-Request-Id**：接口返回头里的 `X-Request-Id`（浏览器按 F12 → 网络 → 点失败的请求 → 响应头；用 curl 则在 `-i` 输出里）。
3. **发生时间**：精确到分钟，写明时区（例如 2026-10-09 14:32 北京时间）。
4. **你在做什么**：场景编号 + 步骤编号 + 你用的账号（姓名，不要写密钥）。

提报格式示例：

```
场景 8 第 3 步 / 账号：李明
现象：按员工分组的金额合计 12 340，按部门分组 12 350
时间：2026-10-09 14:32 北京时间
X-Request-Id：xxxxxxxx
截图：（附）
```

提报对象：**【待填：UAT 负责人姓名 / 工单系统或群名称】**（上线前由负责人填写）。紧急问题（无法登录、整站不可用）：**【待填：值班联系人】**。

提报前先排除"已知限制"（第 3.3 节）：部署期间的短暂不可用、03:00 夜间自动化测试期间的限流、同 IP 登录限流，都不是缺陷。
